# Ticket Overlord Challenge

## Context

You are going to design and build an event and ticketing platform for the Verzel Elite Dev 2026 technical challenge.

The goal is to demonstrate full-stack development, programming logic, product thinking, and the ability to understand and fulfill a real-world request. The scope is intentionally small. The evaluation prioritizes deliberate decisions, a complete end-to-end flow, clear documentation, and evidence of how the solution was shaped over raw feature volume.

Avoid a generic AI-generated interface. AI use is encouraged, but the final result should make the developer's choices visible in the product, code, history, and documentation.

## Product Goal

Build a platform where an organizer publishes an event and a customer buys a ticket.

The organizer creates an event from an external catalog of shows or movies and defines its date, venue, capacity, and price. The customer browses published events, reserves a seat or a quantity of tickets, completes a simulated payment, receives a ticket with a QR code, and can share it through a link. At the venue, gate staff validate the ticket before admission.

## Functional Requirements

### 1. Event Discovery

The product should support:

- Browsing published shows or movies.
- Searching the published events.
- Displaying each event's date, venue, and price.

### 2. Event Management

An organizer must be able to:

- Create an event from a show or movie provided by an external API.
- Define the event's date, venue, capacity, and ticket price.
- Manage the events they created.

The backend must manage calls to at least one of these external APIs:

- [Ticketmaster Discovery API](https://developer.ticketmaster.com/products-and-docs/apis/discovery-api/v2/)
- [TMDb API](https://developer.themoviedb.org/docs)

Using both APIs is allowed but not required.

### 3. Authentication and Roles

The application must provide authentication with three distinct roles:

- **Organizer:** creates and manages events.
- **Customer:** reserves tickets, completes payment, and receives tickets.
- **Gate staff:** validates tickets at event admission.

### 4. Reservation and Inventory

Implement at least one of these reservation models:

- Seat selection through a seat map for a cinema or theater.
- Ticket quantity selection for a general-admission area.

Implementing both is allowed but not required.

The backend must store events, reservations, and tickets and guarantee that the same seat cannot be sold twice.

### 5. Simulated Payment

The checkout flow must handle both:

- Payment confirmation.
- Payment refusal.

No real financial transaction is required. Payment may be fully simulated or use the test environment of a real payment provider.

### 6. Tickets and Sharing

After a successful purchase, the customer must be able to:

- Access a **My Tickets** area.
- View the ticket and its QR code.
- Share the ticket through a link generated by the application.

The QR code must represent a ticket code that cannot be forged.

### 7. Gate Validation

The gate interface must support:

- Reading the QR code through the device camera.
- Entering the ticket code manually as a fallback.
- Returning a clear validation result: valid, invalid, already used, or wrong event.
- Preventing the same ticket from being validated more than once.

## Required Technologies

- **Frontend:** React, with or without a framework such as Next.js, Vite, or Remix.
- **Backend:** Node.js, Python, or Java, using any appropriate framework such as NestJS, Express, FastAPI, Django, or Spring Boot.
- **Database:** Any database distribution may be used. The README must include clear setup and usage instructions for the selected database.

## Non-Functional Requirements

### Deadline

The project must be completed within seven calendar days from receipt of the challenge.

### Documentation

The repository must include a detailed README with step-by-step instructions to configure and run the application. Any incomplete or non-working behavior must be stated explicitly.

### Test Data

Seed enough data for an evaluator to exercise the main flow without configuring everything from scratch:

- One organizer.
- Two customers.
- One gate staff user.
- At least one published event with tickets available.

### Deployment

Deployment is optional, but a working deployment on Vercel or a similar platform adds one point to the final score and makes the project easier to evaluate.

## Optional Scope

The following items are optional and considered positively during evaluation:

- Event search and filters beyond the required navigation.
- An organizer dashboard.
- Cancellation with inventory restoration.
- A real-time seat map.
- Docker Compose.
- Tests.
- A deployed application.

## Out of Scope

The project does not need:

- Invoicing.
- Ticket resale between users.
- A native application.
- Password recovery.
- Ticket delivery by email.

## AI Usage

AI use is encouraged and does not reduce the score.

The repository should explain:

- Which AI tools were used.
- Which parts of the project used them.
- Which work was completed without AI.
- Why important product or technical decisions were made.

Artifacts created during the process, such as specifications, PRDs, BMAD flows, or context files, should be versioned in the repository when they help explain the development process.

## Expected Deliverables

The finished project should include:

- A React frontend.
- A backend built with Node.js, Python, or Java.
- Persistent storage for events, reservations, and tickets.
- Seeded users and at least one published event.
- A detailed README with setup, execution, database, and known-issue instructions.
- Descriptive commits created throughout the development period.
- A public GitHub repository for the final submission.
- Optionally, a deployed application.

The final repository link must be submitted through [elitedev.verzel.com.br](https://elitedev.verzel.com.br/), including where the code is published and how to run it.

## Success Criteria

The challenge is successful when:

- An organizer can create and manage an event based on data from Ticketmaster Discovery or TMDb.
- A customer can browse a published event and reserve a seat or a quantity of tickets.
- The system prevents the same seat from being sold twice when seat selection is used.
- The simulated payment flow clearly handles confirmation and refusal.
- A successful payment produces a ticket with a non-forgeable QR-backed code.
- The customer can view the ticket in **My Tickets** and share it through an application-generated link.
- Gate staff can scan the QR code or type the code manually.
- Gate validation clearly distinguishes valid, invalid, already-used, and wrong-event tickets.
- A valid ticket cannot be admitted twice.
- The seeded data allows the complete flow to be evaluated immediately.
- The README documents setup, execution, database configuration, known limitations, AI usage, and important decisions.
- The result is a simple, complete end-to-end flow before optional features are added.
