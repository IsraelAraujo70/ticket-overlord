# Stack principal e plataforma de deploy

- **Status:** Aceita
- **Decidida em:** 2026-08-10 13:00:57 -03:00

## Contexto

O desafio exige React no frontend e limita o backend a Node.js, Python ou Java. A aplicação precisa entregar autenticação, inventário concorrente, pagamento simulado, emissão de ingressos e validação na portaria dentro de sete dias. O desenvolvedor já utiliza Railway e quer demonstrar decisões maduras sem comprometer o fluxo ponta a ponta.

## Decisão

- Usar um monorepo com pnpm workspaces.
- Usar Next.js, React e TypeScript no frontend.
- Usar NestJS e TypeScript sobre uma versão LTS do Node.js no backend.
- Usar PostgreSQL como banco de dados e fonte de verdade.
- Usar Drizzle ORM, mantendo SQL explícito nas transações e operações de locking que exigirem controle fino.
- Usar Railway como plataforma planejada de deploy.
- Usar `fetch` nativo para chamadas HTTP, sem Axios inicialmente.

As versões exatas serão fixadas durante o scaffold e registradas nos manifests do projeto.

## Alternativas consideradas

### Rust no backend

Rejeitado porque não é uma das tecnologias de backend permitidas pelo desafio.

### Express

É compatível e mais minimalista, mas exigiria definir manualmente convenções para módulos, injeção de dependências, autorização, validação e documentação HTTP. NestJS foi escolhido para fornecer uma estrutura consistente dentro do prazo.

### Stack idêntica à da empresa

Não é exigida pelo enunciado. A prioridade é usar uma opção autorizada, concluir o fluxo e explicar bem as escolhas.

## Consequências

- Frontend e backend compartilham linguagem, reduzindo troca de contexto.
- NestJS adiciona convenções e algum código cerimonial que deve ser mantido fora do domínio.
- PostgreSQL suporta as garantias transacionais necessárias para inventário e validação.
- Railway reduz o esforço inicial de publicação, mas seus serviços e custos ainda precisam ser medidos antes do deploy.
